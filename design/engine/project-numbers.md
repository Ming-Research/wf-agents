Decision: The engine measures how many of a project's works run together from the rounds of the engineer's works on the project's items, counting a work as running only while it has a round under way that is not a wait for an answer (a round at a cell whose step asks the owner or the architect, which stays open for the whole wait), and not counting the architect's works at all, which have no item, hold no slot and run beside the engineer's works, instead of every round under way, because the round of a work waiting for the owner or the architect stays open for as long as the answer takes, so that counting all rounds reports works as running together when none ran, which is the opposite of what the policy's signal about parallel running needs to show. A round of a tool cell counts as running for now, provisionally: a work waiting for CI holds its slot, and the count can be reopened if the owner wants it apart.

Decision: Whether a round is a wait for an answer is read from the compiled flow version its work runs on, which the database keeps for every version a work has run on: a round is a wait when the cell it ran at has, in that version's engineer graph, a step that asks the owner or the architect, and the engine reads each version once for all the rounds measured, instead of a list of cells kept in the engine and held to the current flow by a test, because the flow stays the only definition of which cells wait, a cell added to the flow that waits is counted without any change to the engine, and a round is judged by the version it ran under whatever that version called the cell (the stored versions name these cells differently), which a list needs the older names added to by hand and a test of the current flow cannot check.

Decision: A work stopped before the end of its graph records the kind of its end, in a column of its own written in the same update as the text, from a kind its caller names where the end is written (today the item cancelled and the flow moved to a new version; the kinds started over and other are for the works an earlier engine stopped and for a way of stopping not yet named, so that no caller names them and they stay at zero for new works until a new way of ending a work adds its caller), and the engine counts, for each week, the engineer's works of the project that ended without their item being merged by this work, each once and by that kind, instead of reading the kind back from the text the works table records, or counting items, because a category read back out of prose exists only because it was never kept, the text carries a version number and a clause that differ for every flow move so that it names a kind only by its start, and one place writes every end, so that it can make every caller name its kind. A work that reached the end of its graph without a merged round counts under a kind of its own, derived from its rounds because it records no stop; the one such end the flow has is a work whose architect gave all of it to sub-items, which goes to the end cell without a merge, while a work that delivers a report is merged through a pull request as one that delivers a change is, and has its merged round. Such a work is placed in the week its last round ended, and stays there when its item is cancelled afterwards, because the stop does not move it from the end cell where it had ended already; so a past week's number does not change after the fact for this kind. A work with a merged round never counts, even when its item was cancelled after it, because it ended by its merge. The kinds of works already stopped are filled in once by the migration from the start of their text.

Decision: A week in which nothing ran or ended shows zero for each of these numbers, not a missing value, and the weeks are those the project's other numbers use, instead of a week of its own, because the policy's signals compare these numbers week by week with the others.

Rejected:
- A list of the waiting cells in the engine, with the older ids added, and a test that holds it to the current compiled flow: rejected because it writes down again what the flow says, needs a hand-kept list of older names that no check covers, and the test sees only the current version, so a drift in an older version's name goes unseen.
- A property on the flow's cell that says it waits for an answer, which the engine reads: rejected because it changes the flow's format and the compiler for what the cell's step (asking the owner or the architect) already says, and a version stored before the property would have none.
- Reading the stored versions in the engine's code, deserialized into the flow's types: rejected because it adds a loader and a cache to the engine for what one query over the stored text does, and a version the types no longer read would fail the whole measure.
- The history of which works run, kept in a table of its own: rejected because it needs a write at every place a work starts, waits, pauses or ends, and weeks before it would be empty, while the rounds and the changes already say what the first number needs.
- Rebuilding each work's running stretches from the changes to its cell and its pause: rejected because it replays every change of every work to reach what the cell of an open round already tells, and an older flow version's cell would have to be read by a second rule.
- The kind read back from the start of the text, with the text built and read by one function: rejected because it is still a category recovered from prose, and a writer that does not go through that function is counted as other without anything failing.
- The text of the end replaced by an object holding the kind and the text: rejected because every place that reads the text or tests it for being set would change for nothing a column of its own does not give.
