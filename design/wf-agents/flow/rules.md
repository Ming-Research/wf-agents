- 告诉 agent 的话分四层，各有各的主题：流程的规则，讲 agent 在流程里怎么做事，每个项目都一样，比如工具、CI、证据、
  实验和仓库的整洁，给流程里的每个 agent；共用的返回格式，讲返回怎么交、owner 读的字段怎么写；这套安装的规则，
  即 owner 自己对这套安装的吩咐，放在数据目录里；以及项目的 AGENTS.md，讲只有这个项目才需要的东西，比如它的技术栈、
  构建和测试的细节、它的惯例，在流程里外为这个项目干活的每个 agent 都读它。每个项目都需要的规则属于流程，
  只有一个项目需要的属于它的 AGENTS.md；流程的规则不在 AGENTS.md 里再写一遍，除非流程之外的 agent 也需要，
  因为它们只读 AGENTS.md。这样每条规则只有一个地方，流程也不提任何项目自己的事（第 1 条），
  正如 harness 不涉及任何项目 (wf-agents.md, "wf-agents 只是 harness")；工程师、审查者这类角色本来就在流程里。

- 设计树怎么读、怎么写，是流程的一条规则，给每条读或写设计树的线：工程师、设计者、
  审查者和架构师的线 (flow/rules.md, "告诉 agent 的话分四层")。每个项目的树都在 design/，根是 design/<项目名>.md，
  agent 读到的永远是同一个，项目也不用为它多设一项配置；树用它本身所用的语言写。项目的 AGENTS.md 完全不提设计树，因为设计树是流程的概念，不是项目的；
  助理自己改树的做法，属于助理的指南。写树的格子写的是任何一个项目的树，而别的项目的 AGENTS.md 里没有这些规则；
  写在流程里一次，它们就到达每个需要它们的格子。

- 规则不说流程、工具或权限已经决定的事：谁听谁的、多久查一次 GitHub、行动前先停下来问。角色由流程设定；agent 不轮询
  GitHub，因为引擎跑 CI 并转交结果；agent 能做什么由权限限定。
