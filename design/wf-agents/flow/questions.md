- 留给 owner 的选择是条目上的问题：是非题或单选题，写在条目的问题那一块里 (items.md, "条目分成几块")，是计划的一部分。
  给 owner 的计划在问题所在之处标出它，周围写着它的背景；owner 通过标记的段落看出哪里改了、哪里有待答的问题。
  单独拿出来时，问题既没有背景，在计划里也没有位置。问题不是消息：owner 的回答是对问题那一块的改动，
  之后的格子从输入里读到它 (flow/inputs.md, "条目的各块是有条件的输入")；用 ask 时，设计的选择一经回答就留在了消息中心，
  不随设计的改动而变。它曾叫设计卡，这个名字把几样东西混在一起 (wf-agents.md, "一样东西按它是什么来命名")。

- 只在三条同时成立时才问：两种以上查过的做法都能解决，没有能查证的事实可以定，选错代价大或难以挽回。事实能定的、
  以后改起来便宜的、局部的细节，以及条目本来就要做的事，由 agent 自己定；只有人能提供的东西和条目本身要改的事不是问题，
  走做不下去 (flow/asking.md, "做不下去是条目的工作里每个 agent 格子都有的一条出路")。问题不预设数量，因为它因项目而异，
  只写明常态：多数条目没有，一个常见，两个以上少见。曾有一个条目上留给 owner 的选择多达五个，
  几乎全是记录一个工作做了什么的新决定。

- 问题写明：题目；各个选项，每个写明做什么、代价和风险；推荐的选项；停下等 owner 还是照推荐先做；以及一小段解释：
  停下的，说清缺了 owner 的哪个回答就推进不了，或为什么 owner 改选的可能不小、改选了要返工多少；先做的，
  说清为什么改选了返工也便宜，或推荐的理由为什么足够清楚。曾用过作者有多确定的 1 到 5 刻度，
  它真正起作用的只是 3 和 4 之间那条线，也就是要不要为这份不确定停下，所以问题直接写这一点。

- 停下还是先做，按返工来判断：停下避免返工却耽误推进，先做则相反。没有 owner 的回答就推进不了的，比如复现不了的缺陷，
  一定停下；几条路都不确定、照推荐有较大可能返工且返工代价大的，也停下；不确定但返工便宜的，照推荐先做，
  即使返工也只是小改。

- 卡口只看每个问题的停下还是先做：有一个停下，工作就在卡口等 owner；全是先做，工作就照推荐往下走，
  但合并前每个问题都要有 owner 的回答，有没回答的就在合并处等。卡口是一个引擎格子：直接实现的路上，在设计树那一格之后、
  实现之前；走设计的路上，在设计之后。它只决定工作停不停，不决定 owner 看不看得到：问题和树的改动一写出来，
  owner 就看得到，因为没停下的问题合并前也要 owner 回答。为每个问题都扣住工作，把 owner 的注意力花在了作者有把握的事上；
  而按 owner 从未看过的推荐合并，会把错误的答案扩散到依赖它的条目上。

- owner 在每个问题上要么选一个选项，要么用自己的话提出异议。选了推荐的选项，工作就照常往下走；选了别的选项或提出异议，
  工作就带着 owner 的选择或话，回到写出这个问题的那一格，从那里照常往下走，因为那一格之后的事是在推荐的选项上做的。
  卡口绑在问题上，所以问题上的回答告诉引擎该回到哪一格；讨论里的评论不绑在任何东西上，它只是说话，送到正在运行的格子，
  不改变工作的路线。合并之前 owner 都可以改回答；合并之后就需要一个新条目。

- 重写问题那一块的格子，对没改的问题只交“保留”和它的编号，owner 在它上面的回答照旧；整个写出来的问题算改了，
  owner 在它上面的回答作废；新的一组里没有的问题就此撤回。引擎只看保留还是重写，
  从不判断措辞改了多少 (wf-agents.md, "引擎机械地执行编译后的流程")。

- 工作因 owner 的回答再走的格子，只处理这个回答改变的东西，其余的照旧，这样回去的路很快就走完（第 3 条）；
  这一轮为什么跑，它的标题已经说明 (flow/inputs.md, "每一轮都告诉 agent 这一轮是做什么的")。

- 设计树的改动挂在问题下：会改树的选项下挂着改动的原文，owner 选了这个选项就等于批了它，这样无论 owner 选哪个，
  选项下都已写明树要怎么改；计划立下了以后的工作都要遵守的新规则时，另问一个写不写进树的是非题，原文挂在题下；
  计划与树的某条决定冲突时，另有一个选择题 (flow/engineer.md, "研究不只是从现行的决定往下推理")。
  树的新决定只为这样的规则而立，绝不用来记录这个工作做了什么：那是进度，不是决定。

- 实现把批过的树的改动写进设计树：owner 所选的回答带着的改动，还没选时是推荐的回答带着的，因为工作在此期间照常往下走，
  合并会等这个选择。措辞和位置可以按 main 上最新的文字调整，意思与批过的一致，
  由代码审查核对 (flow/engineer/test.md, "代码审查核对实现写进设计树的内容")：工作进行期间，main 上的树可能已经变了，
  批过的原文不一定能照原样放进去。实现也可以改写问题，或加一个新问题。

- 若一个 branch 的改动触及设计树，而条目上没有哪个问题的回答（已选的或推荐的）带着对树的改动，引擎就拒绝这个 branch；
  代码里有而树没记录的决定，则归审查负责 (flow/engineer/test.md, "代码审查对照设计")：要设计和审查都失手，
  这样的东西才会漏过去。

- 条目被它的设计拆分时，只关系到其中一部分的问题跟着那部分的条目走；关系到多个部分的问题留在被拆分的条目上，
  各部分在那里读它，它只选一次，而不是每部分各选一次。
