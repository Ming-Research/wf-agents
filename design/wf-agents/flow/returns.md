- agent 写给 owner 读的东西用 owner 的语言，以安装时的设定为准，没有设定时用英语，技术术语保留英文原文。
  owner 读它是为了作判断。

- 返回的字段用什么语言写，在返回的 schema 里说明，不写在任何规则里，因为 agent 是按字段的描述来写字段的。

- 返回的每个字段都必须有读者：另一个格子、owner 读的某个页面，或投递其所载内容的消息中心；否则就删掉。显示在条目页上的
  字段带一个标记，编译器把它算作已使用，页面按这个标记显示。这项检查的存在，是为了不让返回里留下无人照看的东西，
  而为了通过检查写一句某个视图读这个字段的备注，会让检查落空。

- 格子的输出必须解决问题：不需要的，agent 就说不适用，不用一份固定的问题清单逼它全部填上。答不了的问题会逼出胡话，
  而这些胡话会成为后面步骤据以行动的东西。

- 每个返回都可以带若干条告知，每条告知说明它关于什么，由消息中心投递。协助者线内部的发现不走这条路。
  返回上的字段不打断任何工作，而用来发送的工具会结束这一轮，因为运行工具就是一次返回。

- agent 在它的返回里报告流程的毛病，依据写在字段描述里的标准，之后没有调试格子或审查，而且这在实际使用中也一直开着，
  直到它再没有任何有价值的东西可报告。标准不需另一个模型就能写进字段里，而这些报告改进了流程。

- 条目的工作中，每个格子的返回是三种之一：这一格自己的答案、要引擎运行的工具，或暂停；
  做不下去是这一格自己的答案的一种 (flow/asking.md, "做不下去是条目的工作里每个 agent 格子都有的一条出路")。
  每个返回还都可以带附带报告和讨论里的回复。只有 owner 能做的、无法挽回的风险和越过的边界，
  各走做不下去或停下等 owner 的问题，所以返回里没有告诉 owner 的话；owner 的话是讨论里的评论，回应它的是讨论里的回复，
  所以也没有回答插话或因插话改道的返回。

- 讨论里的回复只在评论问了什么、需要回应时才写，不回“收到”“照办”，那什么也没告诉读者；
  格子中途也会随工具的结果收到评论 (flow/inputs.md, "条目的各块是有条件的输入")，所以哪个返回都可以带它。

- 条目的工作中，关于流程的报告 (flow/returns.md, "agent 在它的返回里报告流程的毛病") 只跟着这一格自己的答案，
  没话说就整个不写：格子交上自己的答案才算走完，用工具和暂停的返回都在格子中途。

- 条目的工作中，返回不带每轮的进度：条目和工作的状态已经说明它走到了哪里，进度只是同一样东西的第二份 (flow.md,
  "格子之间尽可能共用工具和输出格式")。做到了哪里只在暂停时写 (flow.md, "工作的时间预算用完")。

- 格子只通过它的返回写条目，不用工具：一个格子走完只返回一次，返回里的几处改动按顺序应用；工具调用完会回到格子，
  返回完就走到下一个格子，所以只有真要在格子中途改了再看结果接着做的，才需要工具。写法有五种：整块写；按原文改，
  即给出要换掉的原文和换上的文字，只用于两份计划；问题那一块整组交 (flow/questions.md, "重写问题那一块的格子")；
  背景后面补的那一段整段交，不动架构师写的背景 (items.md, "条目分成几块")；讨论只追加。
  一个格子能写哪几块、怎么写，就是它的返回格式，在图上看得到（第 7 条）。按原文改，改一小处不必把整份计划再写一遍；问题整组交，因为一个回答可能改变别的问题。
