# Settings

The installation's settings as the agents are told them.

### decision a-named-setting-without-a-value-is-refused
A setting that a text sent to an agent names by its key between backticks is given with its value beside the name, where the text is sent: one of the project's that the declaration of the work's project, `flow/project.toml` in its repository, holds, or one of the installation's it names there. A flow is refused as the engine starts where a text sent to its agents names one that has no value, each said against the file or the thing of the flow that holds the text: the parts of each line's system prompt (the line's rules, the engine's own words, and how a cell returns, with the words of each field and of each tool the flow names), each cell's task, what each of its triggers says it does, and the words of each block. Writing `none` beside a setting without a value was turned down.
Why: Given `none` or the name bare, the agent cannot tell a setting the owner left empty from one never set, and the owner learns of it only from what the agent does (principle nothing-passes-for-normal); found as the engine starts, it is mended before any round runs.

### decision a-moved-setting-is-refused-with-where-it-went
Settings that still hold a key the engine moved are refused with words that say where it went, not read under the old key for a while.
Why: The settings are one file the owner writes, with no store of their own that must go on reading as it was; a key read in two places would hold one value under two names (principle one-thing-one-place).

### decision the-installation-names-its-projects
The installation's settings name each project by a table of its own under `projects`, keyed by the name items and the page know it by, with its local repository, its main branch, its check and its host, the host's runners among them; an installation of one project names it as any other, and the tables `[project]` and `[github]` of the one project an installation once had are refused with words saying where each went. What the project is beyond that (its files, its settings, its tests and workflows) it declares in `flow/project.toml` in its repository, which its works' agents are given in place of the one beside the flows.
Why: One installation runs works in several repositories from one store, as the old system ran several projects from one board, so that an item may depend on an item of another project. An installation for each project would split the store those dependencies are read from, and a file for each project in the data directory, as the old engine kept them, would be a second file of settings beside the one the owner writes. What is of the machine (where the repository's checkout is, the token, the runners registered for it) is the installation's, and what the project is travels with its repository (decision every-project-meets-one-contract-for-its-tests).
