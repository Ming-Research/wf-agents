Decision: The ci_before tool runs only the tests it is named, each to its end, in a workflow of its own that the project's configuration names (`ci.before`, a workflow file), and gives the agent for each named test passed with its time, failed with how it ended, or not run with the reason (the tests did not compile on the code before the change, no test has that name, the run stopped before the test, or the log could not be read); the engine pushes the code before the change, with the tests' files and a file naming the tests to run, to a temporary branch whose push starts that workflow and no other, and finds the run by the commit it pushed; a project whose configuration names no such workflow, or whose code before the change has none, is refused with the reason, instead of running the whole fast CI, because the fast CI runs every test of the workspace and stops each job at its first failed test (the default of cargo-nextest), so the tests not yet started have no line in any log, and a test that must fail before the change is the very one an earlier failure cancels; a run of the whole fast CI as a fallback would hide that the project cannot answer.

Rejected:

- Reading the fast CI's logs without narrowing the run: rejected because a test cancelled by an earlier failure has no line in any log, so whatever reads the logs can only say it is missing, and the run also builds, lints and runs everything for tests nobody named.
- An input on the fast CI workflow that narrows the run when the project has it and runs the whole workflow when it has not: rejected because it keeps two modes in one workflow and gives a project without the input an answer that cannot be complete and does not say so; the refusal says it.
- Starting the workflow by hand (`workflow_dispatch`) with the tests as an input: rejected because it needs the permission to run workflows and a second way to find the run, where the push already starts a run that is found by its commit.
- A machine-readable report (JUnit) as the source of each test's result: rejected because in a run that never stops early the line cargo-nextest writes as each test ends, which the ci tool reads already, gives each test's result, and the reason a test did not run comes from the steps of the workflow, which the report does not hold either; a report adds a reader of XML for nothing the lines lack.
