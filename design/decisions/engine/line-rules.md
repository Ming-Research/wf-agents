### decision line-kind-in-the-flow
Whether the agents of a line only read, or change only the project's tests, is said by that line in the flow's definition, never by a cell of it. A line that says neither writes what it will.
Why: A list of line names kept by the engine or by the installation would name parts of the flow outside it, and would go wrong without anyone seeing when a line is added or renamed. The flow is what the owner reads and approves, and its line's file is where the owner sees the line's kind. It is the line's because its agents are told it in the system prompt of the line's session, which every cell of the line shares (principle the-system-prompt-holds-what-a-line-shares). That the kind is said in the flow rests on judgment, not on a case.

### decision a-line-of-tests-is-held-to-what-its-run-changed
As a round of a line that changes only the project's tests ends, its return, of either kind, is sent back for each file that `[tests] paths` of `project.toml` does not take in, of those the work itself changed from the version of the work's head the run began on to the work's head as the round ended: the files of the diff a round is given between two versions of the head, and, where that diff is the whole change against main, only those the two heads differ in. With no version of the head to begin on, the run begins where the branch left main. The line is refused nothing more than a line that writes, and is told the paths of the tests in place of the lock commands. A look that cannot be made, a read of the branch that failed among them, fails the round, and a project that names no tests, or a flow with no block of the work's head, keeps the engine from starting with such a line. This project's paths take in the page's test helpers, `testing.ts` and `fixtures.ts`, but not its mocks, and no Rust source file: the line writes a Rust test in a crate's `tests/` or a module's own `tests.rs`, and where one must go into a source file, it says so in what it hands in.
Why: A return that asks for calls ends its run once taken, and the run entered for the results begins on the head it left, so what it committed would be no later run's change. From the run's beginning, what a round that was sent back left is seen again as the next round ends, and what other lines committed before the run is not the line's; the head the run began on is a version the records keep (principle state-from-records), and the old engine counted likewise from the head the engineer handed over. The diff between two heads leaves out main's code, whoever merged it, and keeps a file put back as main has it. Where the two heads cannot be compared without main's code, the files both diffs name are taken as the run's, which may miss a file the run put back as main has it: a judgment, not a case. The page's design mode runs the mocks, so they are none of the tests, and a test within a Rust source file cannot be told apart from its code by its path. The look, not a refusal, holds the line (principle refuse-as-little-as-must-be), and a lock file is none of the tests. Nothing after the round holds the line to its tests, so a look that failed, a project with no tests or a flow with no head, let through, would take any change for tests (principle nothing-passes-for-normal).

### decision heavy-commands-are-the-projects
Every agent is refused, on every installation, what the files beside the flows refuse every agent, pushing, and the heavy commands of its project's declaration, which every declaration names, none where its project has none; an installation's settings name no heavy command. They name the lock commands that may run under a heavy command, but no lock command that is a heavy command whole or that falls under what every agent is refused. Settings or a declaration that would otherwise undo these rules are refused when they are read.
Why: The engine pushes and has the project checked, and what is heavy is the project's toolchain, which travels with its repository (Article 1): a list kept by the engine named the commands of every toolchain it knew for every project, and none of one it did not. Heavy commands in the installation's settings as well were turned down: they would be a second place for a project's heavy commands, and one list for every project of the installation (principle one-thing-one-place). A declaration that names no heavy commands, taken to name none, would refuse nothing heavy and nobody would see it (principle nothing-passes-for-normal). How wide a lock command under a heavy one may be is the installation's judgment. What stays open: rules in the settings files of the program's own configuration directory, which the engine does not read, and a heavy command the shell reaches by another name.

### decision lock-commands-under-heavy-ones
On a line that writes, the lock commands the settings name, which update a lock file and build nothing, are allowed, even though the heavy commands they fall under are refused. Where the installation allows some other use of such a heavy command, the engine refuses that use again. Where the installation allows the whole heavy command, or every command, the heavy command is refused whole and its lock commands are not allowed.
Why: Agents that could not regenerate a lock file wrote it by hand, or stopped and waited for someone. But the command line refuses whatever any rule refuses, so refusing the heavy command whole would refuse its lock commands as well, and leaving out the refusal without refusing the installation's rules again would let a build through.
