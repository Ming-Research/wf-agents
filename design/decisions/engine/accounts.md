# The accounts

The accounts the agents' program makes its calls under, which the owner adds on the page and switches between.

### decision an-account-is-a-name-and-a-token-in-the-keychain
An account is a name the owner gives and a token the agents' program makes to last a year (`claude setup-token`), kept in the macOS login keychain as a generic password, under a service of the installation's own and the account's name, and written, read and deleted by `/usr/bin/security`, the token given on its standard input and never among its arguments. The token is in no file of the repository or the data directory, no setting, no record of the store, no log and no words of an error, and no answer of the page's interface holds it. A token is checked by the check of the outside under it before it is kept: one the service refuses, or one that could not be checked, is not kept.
Why: The keychain keeps it encrypted at rest, where the program keeps the same kind of token; a file readable by its owner alone under `~/.wf-agents`, as the token of GitHub is kept, was turned down for lying open on the disk. Reaching the keychain through the Security framework from the engine was turned down: an item trusts the program that made it, and the engine's binary changes with every install, so the owner would be asked to allow it again after each, in a dialog a login service shows to nobody (a judgment, not a trial). An item made through `/usr/bin/security` can be read by any program of the owner's user through that command, as the program's own sign-in can.

### decision the-account-in-use-is-the-engines-own-state
Which accounts there are, and which is in use, are records of the store only added to (an account added, removed, taken), the engine's own state as whether sessions are kept warm is: the driver reads them as it opens and changes them as the owner acts, and the page asks the driver. The account in use is the latest taken that was not removed since; with none, the agents run on the sign-in of their directory of settings, which holds the program's settings and sessions under every account. A name taken by an account not removed is refused, and the account in use cannot be removed. A token is kept before its account is recorded as added, and let go of after its account is recorded as removed.
Why: The page changes the account while the engine runs, and the engine reads the settings' file only as it starts: kept in the file, as the directory the agents ran in was, a switch would wait for the next start. Records only added to say what each try ran under as of any moment (principle state-from-records), and kept in that order an account recorded never lacks its token, while a token left behind by a removal names nothing (principle effects-known-as-done).

### decision the-account-is-handed-out-with-the-round
Every round is handed out with the account in use as it is handed out: each try of it records that account by its name as what it ran under, and the program is given that same account's token, so that what is recorded and what is given are one value; a round handed out before a switch runs under the account it was handed out with. With no account in use a try records the directory of the program's settings, which, holding a `/`, is never a name, and no token is given. A keep-warm ping runs under the account in use, which its session's last call ran under; a fork under its session's last account, or under the account in use where that one was removed, saying which was removed; the check of the outside under the account in use. A token that cannot be given fails the round as a command line that cannot run, in the words of what keeps it, and the program is not run.
Why: Read again by the carrier as a try begins, the account a try records and the one whose token it is given could part across a switch, and the records would say a round ran under an account it did not. Falling back to the directory's sign-in where a token is missing would run the round under another account than the one recorded, unseen (principle nothing-passes-for-normal).
