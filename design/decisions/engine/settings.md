# Settings

The installation's settings as the agents are told them.

### decision a-named-setting-without-a-value-is-refused
A setting that a text sent to an agent names by its key between backticks is given with its value beside the name, where the text is sent: one of the project's that the declaration of the work's project, `flow/project.toml` on its main, holds, or one of the installation's that `agents/installation.toml` beside the flows names. A flow is refused as the engine starts where a text sent to its agents names one that has no value, each said against the file or the thing of the flow that holds the text: the parts of each line's system prompt (the line's rules, the engine's own words, and how a cell returns, with the words of each field and of each tool the flow names), each cell's task, what it does when each datum it watches is new, and the words of each block. Writing `none` beside a setting without a value was turned down.
Why: Given `none` or the name bare, the agent cannot tell a setting the owner left empty from one never set, and the owner learns of it only from what the agent does (principle nothing-passes-for-normal); found as the engine starts, it is mended before any round runs.

### decision a-moved-setting-is-refused-with-where-it-went
Settings that still hold a key the engine moved are refused with words that say where it went, not read under the old key for a while.
Why: The settings are one file the owner writes, with no store of their own that must go on reading as it was; a key read in two places would hold one value under two names (principle one-thing-one-place).

### decision the-installation-names-its-projects
The installation's settings name each project by a table of its own under `projects`, keyed by the name items and the page know it by, with its local repository, its main branch, its check and its host, the host's runners among them; an installation of one project names it as any other, and two projects that name one repository are refused as the engine starts. What the project is beyond that (its design tree, its files, its settings, its tests and workflows, and its heavy commands) it declares in `flow/project.toml` on its main, read as the engine starts, which its works' agents are given in place of the one beside the flows. Which of the installation's settings the texts may name, and what every agent is refused whatever its project, are the flows', in `agents/installation.toml` and `agents/refused.toml` beside them, read once for every project.
Why: One installation runs works in several repositories from one store, so that an item may depend on an item of another project: an installation for each project would split the store those dependencies are read from, and a file for each project in the data directory would be a second file of settings beside the one the owner writes. What is of the machine (where the repository's checkout is, the token, the runners registered for it) is the installation's, and what the project is travels with its repository (decision every-project-meets-one-contract-for-its-tests). The declaration is read from main, where works branch from, since the engine never moves the checkout of a project hosted elsewhere. The texts that name the installation's settings, and what every agent is refused, are one set for every project: listed in each declaration, the list would be copied into every repository, and one project's copy could keep the whole installation from starting. Two projects in one repository would share its main, its branches and its merges.

### decision the-carriers-own-variables-are-refused-in-agents-env
The settings are refused as the engine starts where `agents.env` names one of the carrier's own variables (the token's, `CLAUDE_CODE_OAUTH_TOKEN`; the directory's, `CLAUDE_CONFIG_DIR`; the scrub's, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`), or a credential the agents' program takes above the token (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`).
Why: Named there, the engine's own value would reach the program beside or above the carrier's, and the rounds would run under what their records do not say: a credential above the token would have every call run under it and not under the account it was handed out with, where the program runs under no credential but the owner's accounts (decision no-default-credential). Closing the accounts while one is named, and letting the installation run on it, was turned down for that.
