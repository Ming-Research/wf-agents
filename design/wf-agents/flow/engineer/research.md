- 工作从理解条目的那一格开始：它弄清条目要解决的事，再为这件事读设计树，只读与它有关的节点和决定，
  连同它们的理由和走不通的路 (flow.md, "设计树读来是为了知道定了什么")，需要时辅以代码，
  不强制也不限制 (flow.md, "要理解某样东西，agent 既读代码")。初步研究用同一个模型，在同一个 session 里接着做，
  读过的树还在 context 里，不再读一遍。读树单独成一格，因为 agent 不读或不深读设计树，而这一格每个工作只多一轮，
  读过的树又留给初步研究用 (flow.md, "审视流程和往流程里添加东西用同一个标准")；它只读与这件事有关的部分，
  因为这一格不能跑得太久。弄清条目要解决的事也在这一格，因为它本来就要为此读树。

- 理解条目的那一格只在发现现有背景没提到的、不简单的重要信息时，才重写条目的背景 (items.md,
  "条目上给 owner 看的块用 owner 的语言")，最多 300 字；否则不写。背景本来由架构师写好，
  而条目只需一点背景 (items.md, "条目分成几块")。

- 理解条目的那一格还写下与条目要解决的事有关的决定，最多 10 条，每条一行，用英文，只在 session 中途重开时交给初步研究：
  平常初步研究延续这个 session，读过的树都还在 (flow.md, "延续另一个格子的 session 的格子")。

- 在理解条目的那一格、深度研究和实现各自开始之前，都先把工作的 branch 更新到最新的 main，使任何阶段都不在旧代码上工作。
  session 延续下来的阶段会收到 main 改动过的文件，因为 session 记得旧版本，列出来它就知道要重读；
  在新 session 中的阶段读的是代码现在的样子，不给它这些。

- 初步研究弄清怎么用代码做成条目要做的事，即理解条目的那一格之后剩下的事。它的结果写在条目上：两份计划和问题，
  问题是计划的一部分 (flow/questions.md, "留给 owner 的选择是条目上的问题")；以及往下怎么走，直接实现还是走设计。
  写出树的改动，交给设计树那一格 (flow/engineer/research.md, "直接实现的工作在初步研究之后都经过设计树那一格")；
  条目本身要改，走做不下去 (flow/asking.md, "做不下去是条目的工作里每个 agent 格子都有的一条出路")，不停下来问架构师。
  这几件事分在几个格子里，因为需要专注的判断要单独成一步 (flow.md, "需要研究和专注的判断")。

- 给 owner 的计划不限长度，不定格式，以把事情讲清楚为准，不长篇大论，可以用图；给 agent 的计划怎么写，
  由 agent 自己定 (items.md, "条目上给 owner 看的块用 owner 的语言")。定死的格式会逼它们填上用不着的东西
  (flow/returns.md, "格子的输出必须解决问题")。

- 初步研究可以使用 CI 和各种工具。不实际运行，它找不到根因。

- 让研究只做研究的，是交给它的任务，而不是它可以写在哪里。它为问题做出来的东西，数据、代码、探针和笔记，放进研究目录，
  不散落在别处；复现问题的测试放在项目的测试所在之处，这样它在那些测试运行的地方运行，实现也会保留它。
  简单的研究只留下结论；确立了超出本工作的规则的结论，要问一个写不写进树的问题 (flow/questions.md,
  "设计树的改动挂在问题下")。为了让研究守住本职而把一切都限制在研究目录里的做法，也让复现无法在测试运行的地方运行，
  于是缺陷在修复之前无法被看到发生。

- 初步研究能定下方案时，就把它写成计划，走直接实现的路；只有定不下来时，才接着做深度研究。大多数工作在这里就定了，
  需要更多的是棘手的性能问题、要设计的功能或顽固的缺陷。另加两个格子分别追问根因、以及是否属于设计缺陷的做法被否决了：
  对大多数工作（比如少了一行 CSS）问这些毫无意义，而且与深度研究重叠。

- 只有真正需要的工作才做深度研究，绝不为了求一个批准而做。把事情提交批准就够了，为此走一趟深度研究是浪费。

- 初步研究有办法停下来，而不是硬撑到一个勉强的结论；是否接着做深度研究，由工程师能理解的原则来决定，而不是由硬性指标。
  即使是勉强完成的初步研究也有结论，它可能看不出这个结论站不住；硬性指标则会漏掉很多情况。

- 有疑问时，初步研究继续往下查，而不是停下来问；看不到缺陷发生时，把怎么继续写成问题 (flow/engineer/research.md,
  "缺陷只有在它显现的地方被看到发生之后才修")，真正的选择也写成问题 (flow/questions.md, "只在三条同时成立时才问")。
  问架构师得不到多少额外的东西，而停下来代价很大。

- 缺陷不需要设计：力气花在它是怎么产生的、如何预防、修复是否可靠，以及是否由架构上的缺陷引起。
  设计是为不确定的需求定路线的。它是怎么产生的，要追到源头，写进研究交接出去的内容里，因为在源头上弄明白的缺陷，
  怎么修就一目了然；这不单独发消息，因为大多数缺陷都是测试没覆盖到的情况，流程中的哪一步都拦不住。

- 深度研究做多深取决于工作：改动波及面广时，agent 先理解系统；非常局部的改动可以不看架构就改。
  agent 不记得 owner 的意图，也不记得之前的 agent 想过什么，上来就改可能把东西改坏；局部的事情不值得为它去读架构。

- 缺陷只有在它显现的地方被看到发生之后才修，比如在真实浏览器的页面上，或在程序用它自己的数据运行时。无法为它写测试时，
  比如只偶尔出现的问题，就不强求：探针、日志或 owner 亲自运行都可能让它显现。查遍工具所及之处，
  仍然在哪里都看不到的缺陷，不管是工具够不到它显现的地方，还是状态后来变了，都会让工作停在它所在的研究上，
  之后不做深度研究，而是把怎么继续写成一个停下等 owner 的问题：按推测的原因修、等 owner 给出复现的条件，或关掉条目。
  那时并不知道是不是工具不够，而深度研究的工具也一样。曾有一次，推断出的原因被修复后，在浏览器的替身里通过了测试，
  缺陷却还在，后来又作为新条目回来了（第 2 条）。

- 工作接手做了一半的东西时，初步研究会拿到可供查看的线索，先看做到了哪一步，再照常研究；已有的东西是保留还是改动，
  由工程师判断。做了一半的东西可能来自另一个流程或另一个 agent，没有同一张图可以对比，
  所以因为定义及其输入没变就机械地跳过格子，会出错。

- 直接实现的工作在初步研究之后都经过设计树那一格，接着初步研究的 session 做：
  它为问题写出设计树要的改动 (flow/questions.md, "设计树的改动挂在问题下")，补出初步研究漏掉的计划与树的冲突，
  都没有就写不改。它不把工作退回初步研究，冲突都成了由 owner 选的问题。之后是卡口，
  再是实现 (flow/questions.md, "卡口只看每个问题的停下还是先做")。每个直接实现的工作都走这一格：初步研究漏掉的冲突，
  只有专门去看才找得出，而这一格接着同一个 session，只多一轮 (flow.md, "审视流程和往流程里添加东西用同一个标准")；
  初步研究只管把怎么做成弄清楚。

- 树的改动不空时，设计树那一格之后是对这些改动的审查：它从理解条目的那一格读完树之后的 session 派生，
  有那一格为这件事读过的树，也走缓存，却看不到初步研究和设计树那一格的思路；它只提意见，
  一次提完 (wf-agents.md, "检查一次报出它发现的所有问题")。初步研究每走一次，设计树那一格最多走两次，审查只走一次：
  第二次逐条处理审查的意见，采纳就改，不采纳就说明理由；意见和回应只留在轮的记录里，
  不上条目 (items.md, "条目分成几块")。只经作者检查的改动，曾给后来的审查留下矛盾；
  这样派生的审查者对树知道得不比作者少 (flow/engineer/test.md, "审查者的能力和知识不低于工程师")，
  又不被作者的思路带着走。

- 深度研究和顾问一样，使用比条目的模型高一个级别的模型，而走这条路的工作很少。用条目的模型，
  较弱的 agent 可能修了表面就停下，掩盖了更大的问题，而它忽略的东西，流程在别处再也找不回来。

- 设计不先编出几种方案来比较：它理解上层的决定，想清楚对这个问题什么是合理的，只有真的存在另一个方向时才比较。
  有些问题显然只有一种合理的做法，编出来的比较是空洞的。

- 设计完成后，要再审视一遍，找更好的设计 (flow.md, "为问题选定的方案本身也必须受到质疑")：通往同一目的的另一条路，
  或以更简单、成本更低、维护更少的方式达到同一目的，包括设计树排除的方式。若有值得其代价的，就把设计整个重写，
  取代第一版；否则第一版不变。改为追问设计哪里没想透，很少能推翻前提（86 份方案中只有 2 份），而要求找更好的设计，
  在大多数设计中都找到了。

- 深度研究之后，没有需要逐个回答的岔路口问题：它对现行决定的偏离写成问题 (flow/questions.md,
  "留给 owner 的选择是条目上的问题")，其余的留给审查。

- 一个工作装不下的设计，若能分成各自可以独立完成和合并的几部分，就经由专门的出路离开深度研究：
  引擎通过消息中心把拆分交给架构师，并把工作扣在那里，直到架构师把该条目变成统领各部分的目标（这会结束该工作）、
  把第一部分留给该工作并把其余部分建为条目，或说明原因后拒绝（这会让工作回到深度研究）。拆分条目是架构师的职责
  (flow/architect.md, "架构师的职责是与条目和观察有关的一切")，格子的输出所要求的停顿画成一条出路，
  而不是留给 agent 的 ask（第 7 条）。
