Decision: The engine's loop is the only scheduler of the works: between steps it alone reads what the owner asked, carries out the outbox, brings works to the flow version it runs, starts works and hands out slots, and it runs each step it dispatches on a thread of its own with a database connection of its own, never two steps of one work at once, so that the rounds and tool runs of different works overlap while each work still moves one step after another and the owner's pause of a work still takes effect when its round under way ends; instead of the loop taking one step of one work at a time, because a step waits on an agent's command line or on a CI run for minutes, and while it waited every other work stood with its slot taken and unused (observed in the owner's database: no two works' agent rounds or CI runs ever overlapped while several works were alive together).

Decision: Only the loop hands out slots: a work that holds no slot, because it waits, takes one for a step only when the loop grants it a free slot as it dispatches that step, and the step's own check whether the work may leave its wait reads that grant, instead of each step counting the free slots itself, because two steps counting at once would both see the same free slot and go on beside the works that hold the others, or, each counting the other as holding one, neither would go on.

Decision: Whatever runs an agent's command line for a work, a step or a ping that keeps its session warm, is dispatched by the loop as that work's one job in flight, and the session manager still refuses a ping beside an open round of the session, because a ping and a round of one session at once would interleave two turns in one conversation, and a ping run on the loop's own thread would hold up every dispatch while it ran.

Decision: Git commands on a project's shared checkout (fetching main, adding and removing a work's worktree) run under a lock of that checkout held in the engine's process, instead of a clone of the repository for each work or retrying when git refuses, because git takes lock files in the checkout for these commands and fails at once when another command holds them, while a clone for each work would fetch the whole repository again for every work.

Rejected:
- Splitting each step into preparing, waiting and finishing, with only the waits moved off the loop's thread: rejected because every step that waits (an agent's round, each CI tool, the merge, the watch of main) would have to be suspended and resumed with its state kept between the parts, a complexity forced by keeping one thread rather than by the problem, while a step on a thread of its own stays one straight function.
- An asynchronous engine on an async runtime: rejected because every function of the engine, the session manager and the GitHub client would turn asynchronous while the database library stays synchronous, for no more concurrent steps than the machines have slots.
- A process for each work: rejected because the page's live events come from commits on the engine process's connections, and the configuration, the halt and what the owner asked would have to cross processes, an isolation nothing needs while one machine runs the flow.
- A thread for each work that loops over its own steps: rejected because pausing, the halt, the owner's Step and the slots would then be decided in every work's thread instead of in one place between steps.
