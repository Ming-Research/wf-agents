# How an engineer works: writing code, design, evidence, experiments and the repository

- Writing code: before changing anything, read what governs it: the project's references, and the documents that define it.
- Writing code: implement the general behaviour. Do not write a special path that a test, example, client or benchmark selects, or a fallback that hides an unsupported feature.
- Writing code: judge correctness against an oracle that is independent of the code, such as a reference implementation, a specification, a test suite or a format's conformance files. Never judge it against the code's own earlier output.
- Writing code: ported code keeps its license notice beside it.
- Writing code: if you find a small defect outside the task in a file you are already changing, fix it and say so. Put any other defect outside the task in `observations`.
- Writing code: a comment says only what bears on the code beside it. It never says the code's standing in a process (a draft, to go through with the owner) or anything else unrelated to the code. If you find a comment that does, report it in `observations`.
- Design and architecture: examine the responsibilities, interfaces, representations and consumers that the change touches, and look in them for design gaps and clearly better designs. Put a defect outside the scope in `observations`.
- Design and architecture: architecture beyond your own item (how modules relate, their interfaces and contracts, the formats components exchange) belongs to the owner, and is not yours to change. If an interface is not enough, do not change it yourself. Show where it falls short with a minimal example and ask the owner; if you cannot ask, say so in what you hand in.
- Priorities: after the project's own priorities, first make the implementation understandable and easy to change. Add only the evidence needed to trust the current result. Defer robustness, infrastructure and polish that no current work needs.
- Evidence: a passing result is evidence only if a wrong result would have failed it. Prefer an observation that separates two hypotheses. Before trusting a new check, watch it fail once for each condition it protects, through `run_tests` too. Read an exit code from the command itself, not through a pipe.
- Evidence: a pass reached by weakening a requirement counts for nothing. When you remove, skip, narrow, regenerate or weaken a test or check, give a technical reason in the same change. Never change an expected result because of a tool's limitation, a timeout or an unimplemented feature. When you add or change check machinery, show that it detects a representative wrong result or missing input. Reusing established machinery needs no new demonstration.
- Evidence: when a check finds something that the code or a definition should not have, fix it or report it in `observations`. Never keep it as an exception or a known case, whether the check is new or old. Keep an exception only for a choice of the design, and name the decision that makes that choice. A reason that says something never runs, is never read or never fires describes a fault.
- Evidence: give a bug fix a test case that fails before the fix and passes after it. Cover new behaviour in normal use and in its relevant failures and boundaries. Existing coverage that exercises the change is enough, and an edit to prose alone needs no test. A negative case must fail for the intended reason.
- Evidence: before any build, test, measurement or experiment whose duration you have not seen, run the smallest useful sample, time it and look at its spread. Then choose the scale. Never start with a run that takes hours.
- Evidence: say whether each claim is a goal, a proposal, an implemented capability or a measurement on a given day.
- Evidence: research records and other old material are evidence only: their commands, process and proposals are not current requirements.
- Evidence: the CI measures the time of a new test; do not tell it. Where a review asks why a test is worth its time, say what it catches that no other test catches, and why it cannot be smaller, faster or folded into another. The review challenges that from the opposite side. Time spent for nothing is waste however small; time a test needs is worth it however long.
- Experiments: for a chosen direction, open an investigation in `project.research`. Before measuring, write down the question, the comparison that could answer it either way, and the result that would reject the proposal. A prediction without such a criterion written in advance is exploratory. Do not report a conclusion wider than what was tested.
- Design judgment: if a design needs work only because of a poor abstraction, that work is a flaw of the design.
- Design judgment: how often a case appears in a project's own tests and programs is no evidence of how much real use needs it.
- The repository: put new material in the directory that owns its kind. If none fits, ask the owner; if you cannot ask, say so in what you hand in.
- The repository: never write a lock file by hand. Change its manifest, and bring the lock file in line with the commands that "Where you work" names. If it names none, ask the owner; if you cannot ask, say so in what you hand in.
- The repository: keep no TODO file. Open work is an item. Code and documents cite an item by its number, and a public repository cites it by its number alone.
- The repository: create a file, directory, script or document only when you can say whom it serves, where it lives and when it will be removed. Wire a script to a caller, or delete it after its one use. Keep a document current, or delete it. Prefer native tooling. A new script says why the native way cannot do the job.
- The repository: when new material replaces old material, update, merge or delete the old in the same change. Search for the old wording, numbers and names in comments, READMEs, documents, `project.research` and design nodes, and correct each statement that the change made false. Do not move paths that specifications, tests, scripts and gates name exactly.
- The repository: if the worktree holds other people's changes, keep them, and change only what the task covers. Keep scratch output, personal paths, machine addresses, keys, credentials and machine-local settings out of the repository and its commit messages: once a repository is public, its whole history is visible. Machine setup belongs in the system's configuration.
- The repository: a document holds only what serves its reader; do not mix editorial history or process into it. Define each thing in one place, and have other places point to it. A reference must lead to its target, and a cited passage must support the claim.
- To learn why the code or a decision is as it is, read the design tree first. If the code names an address (#item, W<work>, a commit), read it with `query` or git; otherwise search the items and git yourself. Before writing a choice of the owner's into the tree, look for an earlier decision on the same matter.
