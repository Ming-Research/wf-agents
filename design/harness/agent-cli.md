Decision: An agent's round runs as one call of an agent command line in its print mode (`claude -p` and the like), resumed in the same session for the next round, instead of an agent software development kit, because the owner can then switch accounts in a terminal and switch to another vendor's command line, and which command line runs and how it starts is configuration.

Decision: Each line of a work (the engineer, the review, the adversarial tester, the advisor) goes on in its session, which the command line compacts itself when it fills within a round, and the session manager starts the line a new session where the flow says (the engineer's at implementing and at fixing) and once its session's context is past the configuration's limit, instead of one session per line for the whole work, because a session read again whole at every call grows the cost of each call with the work (see the session manager's node).

Decision: The command line is given one structured-output schema that is the same for every cell of a graph, made from the graph alone (the return's top-level fields with their types; the field of the form an object holding none of the fields beside it; required, that field and those beside it that no form of any cell leaves out), while the cell's own schema goes in the prompt and the engine checks the return against it and says where it does not fit, instead of the cell's schema as the command line's structured-output schema, or one whose required fields follow the cell's forms, because the command line places that schema with the tool definitions, so a schema that changes from cell to cell invalidates the prompt cache at every change of cell: the architect's rethink after a batch, whose forms all hold `progress`, was given a schema that required it, and read nothing of its session from the cache, writing 212,661, 236,140 and 138,702 tokens again (about $0.55 to $0.95 at Sonnet at the end of every batch), while every other round of the line read it; and a field put inside the form's field is refused by the command line within the round, instead of by the engine after it.

Decision: Every agent's cell of a line gives its command line the same parts the command line puts before the session (the program and its arguments, the model, the structured-output schema, the tools and commands refused, the directories added, the configuration directory and where it runs), the effort aside as far as the flow's check allows, and a test goes over every cell of every line of the flow to hold it, instead of a test of the rounds one scenario reaches, because the prompt cache was lost more than once by one cell whose command line differed from the rest of its line: once by the effort low mixed in, once by a schema that required a field all the forms of one cell held.

Decision: An agent asks for the GitHub and database query tools by handing in `tools`, which the engine runs in its tool cell and gives back in the next round, instead of tools the agent calls in the middle of a round, because to the model either is one tool call, and going through the tool cell records every run and checks it against the list of allowed commands.

Decision: The command line reads only the settings of the agents' own configuration directory (`--setting-sources user` for `claude`), so it reads no project instructions or project settings by itself, such as the worktree's AGENTS.md, instead of reading them as a session started in a project directory does, because the engine gives the project's guide as a material once in a session, and a guide the command line reads by itself comes twice and comes back in every session whether the session needs it or not.

Decision: What the agents of each line may not do on the machine is in the installation's configuration, with defaults, and every round's command line refuses it as tools and commands: no line runs heavy work (compiling, type checking, building, test suites, benchmarks, measurements: cargo, rustc, make, tsc, npm runs, npx and the like) or pushes, and the review, the advisor and every line of a project's architect only read, editing no file and committing nothing, instead of the command line's arguments refusing a few commands for every line alike, because heavy work goes to CI however convenient running it here looks, and a role that only reads must not be able to change the work it reads.

Rejected:
- Starting the command line bare (`--bare`), which also reads no project instructions: rejected because it takes only an API key, not the account the owner logged in with.
- A structured-output schema of a bare object: rejected because the model then handed in the nested objects as JSON strings, seen on three returns in a row.
- Tools served to the agent in the middle of a round: rejected because it saves the model nothing, and the costs of handing back (fields a return must carry, a restart of the command line) belong to how a return is handed in and can be cut there.

Decision: The directories outside the worktree where the engine saves what it gives agents by path (`tool-output`, a tool's result too long to give inline, and `logs`, the logs of red checks) are added to every round's command line with `--add-dir`, by their real paths, and edits there are refused with `--disallowedTools "Edit(/<path>/**)"`, a path that starts with two slashes being absolute and an Edit rule covering every tool that edits a file, instead of paths the agent was given and could not open, because Claude Code lets its tools reach only its working directories, and a result the agent cannot read is no result. This works around the command line's permission model, which has no read-only working directory: `--add-dir` lets its tools read and edit there, and in the `acceptEdits` mode its own filesystem commands (mkdir, touch, rm, rmdir, mv, cp, sed) run there without asking; the Edit rule refuses the file-editing tools and writes Claude Code recognises (such as tee and redirections), but not those commands, which a rule on a path does not reach. So an agent can read every file in those two directories, and can still copy, move or delete one there with a shell command, though not edit it with a tool.

Decision: Every line of a project's architect only reads, as the review and the advisor do: the one its works go on in, the review of its item changes, the search of observations and the setting of a policy; what it changes, it changes through the engine. Its command line runs in a worktree of its own of the project, detached at the project's main, one for each of the architect's graphs (`worktrees/<graph>/<project>`: that of its works, whose lines take turns in it, and the setting of a policy's, which goes on beside the architect's work, so that one's refresh moves no file the other reads), which the session manager fetches and brings to the latest main before each round, dropping whatever was changed there; another branch it reads there with git, without switching (`git show origin/<branch>:<path>`, `git diff origin/<main>...origin/<branch>`, `git log`), and gh for a work on no item runs there, where gh knows the repository. The new architect that reads a policy, which knows only what it is given, runs in an empty directory of its own (`worktrees/<cell>/<project>`) and is told of no worktree. This is instead of a directory of its own with the project's checkout added to what the line of the architect's works may read, because the checkout stands on whatever branch its owner left it, the setting of a policy, whose study reads the code, could read none of it and read GitHub's default branch instead, and gh in a directory that is no repository knows no repository.
