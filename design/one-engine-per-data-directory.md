Decision: One engine runs per data directory, enforced by an exclusive operating-system lock on a file in the data directory that the engine holds for as long as it lives, because the operating system releases the lock when the process ends in any way, so a crash leaves no state to clean up or to judge stale, and the answer is exact where a recorded process id can name a dead or recycled process.

Decision: The held lock is a value bound to the data directory it guards, which the engine's constructor requires and takes its data directory from, and it is taken before the database is opened or any other file of the data directory is read or changed, instead of a check made by the run command, because then no caller can build an engine without the lock of its own directory, a refusal is an error of its own and not one of the construction errors, a command that must exclude the engine can take the lock without building one, and a refused start changes nothing, including the stop file that a running engine is watching.

Rejected:
- Lock taken only in the run command: rejected because the guarantee then lives in one caller; any other code that builds an engine runs unguarded and nothing tells its author, while the held-lock value makes the engine type itself carry the guarantee.
- Lock taken inside the engine's constructor from the data path: rejected because the lock then cannot be taken without building an engine, so a command that must exclude the engine, or a test of the lock alone, needs a configuration, an agent and a hub, and a refusal is one error string among the construction errors; the lock as a value of its own keeps the refusal separate and makes the order visible in the caller.
- Lock owned by the database layer: rejected because the guarantee covers more than the database (worktrees, the effects of the outbox, the agents), and it would make the database layer aware of processes; protecting the schema from other commands is a separate decision.
- Process id file with a liveness check: rejected because a crash leaves the file behind, so every start must judge whether the recorded process is alive, which needs a spawned helper or a platform-specific lookup, can mistake a recycled process id for a live engine, and still races when two starts replace a stale file; the kernel lock has no stale state to judge.
- Lease row in the database with a heartbeat: rejected because a round runs an agent for a long time inside one call, so the lease must outlast the longest round or be renewed from a second thread, a restart after a crash is refused until the lease runs out, and it rests on clocks that err in both directions; the kernel lock is exact and needs no schema change or migration.
- Byte-range lock whose holder the kernel reports: rejected because it adds a dependency with platform differences, the lock is dropped when any descriptor of the file is closed anywhere in the process, and two handles in one process never conflict so even refusal needs a child process to test; the whole-file lock from the standard library has none of these and the holder's identity only decides the wording of a message.
- Socket the engine listens on: rejected because a socket file survives a crash and a stale one must be told from a live one by a race between two starts that needs a lock anyway, the socket path length is limited on some platforms, and a control channel is a separate decision from keeping a second engine out.
