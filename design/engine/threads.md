Decision: The engine's state is split in two: what lasts across steps and is the same for every step (the compiled flows read so far, the configuration in use, the wait that halts every work and the kind of failure the owner was told of once, the owner's global pause as the loop last handed it, the works held for a slot and the works taken over, the session manager with the new sessions the owner asked for, the agents' command line, GitHub, the callbacks that tell the page and the log what runs, and the commit listener) is one shared part behind an `Arc`, each piece of it safe to share between threads (`Send + Sync`), and each thread that takes a step has an execution context of its own that holds the shared part, its own connection to the database with the shared commit listener registered on it, and the configuration as it stood when its step began; the rounds a step reports it took are those its context's connection started or changed in transactions committed since the step began, as SQLite's hooks on that connection record them; instead of one engine value with one connection that only the thread owning it may use, because a step of one work can then run on any thread beside the steps of others while each step stays the same straight synchronous code on a connection of its own, and SQLite already lets connections of several threads write one database one at a time (an immediate transaction takes the write lock before it reads, so the number of the change it records is never taken twice), as the owner's page already writes it from a connection of its own for each request; and instead of the rounds of every connection compared before and after the step, or of the works the step named, because only the step's own connection tells its rounds apart from those another thread's step or the page writes meanwhile, a round of another work the step cut off included, without a list of the works each step touches.

Rejected:
- One lock around the whole engine, taken by the thread that takes a step: rejected because a step holds the engine for the whole of an agent's round or a wait on CI, so the steps of different works would still run one after another.
- One engine shared by reference, every method taking it shared and borrowing a connection from a pool: rejected because the reads and writes of one step could land on different connections, and which state is shared and which is the step's own would no longer show in the types.
- One thread owning the only connection and doing every read and write the others send it: rejected because each of the engine's reads and writes would become a message and a reply, and a step's reads and the decisions it takes on them could no longer sit in one transaction.
- A child process for each step: rejected because the halt, the failure told once, the owner's asks for new sessions and the page's live events would all have to cross processes, and each step would compile the flow and read the configuration again.
- Each function that starts or ends a round noting it for the step: rejected because such a function sees only a transaction, the note of a write rolled back would have to be taken back, and code that comes to write rounds later could leave the note out, while the connection's hooks see every committed change.

Decision: A git command of the engine's that changes what every worktree of a project's repository shares (a fetch or a pull, which moves the remote-tracking branches; adding, removing or pruning a worktree, which writes the repository's list of worktrees and, for a new branch, its configuration; and a branch, configuration or remote command, which writes the configuration, as deleting a branch drops the branch's section) first takes a lock of the engine's process for that repository, found by the repository's common git directory, whichever of its worktrees the command runs in, the subcommand read past git's own options; instead of only the commands run in the project's checkout, because every worktree of a project shares the checkout's git directory and a fetch run in a work's own worktree moves the same remote-tracking branch as one run in the checkout, while git does not wait for a lock file another command holds: with the configuration's lock file held, a command that writes the configuration fails at once, and a branch deleted keeps its section in the configuration with only a warning and a successful exit, which no caller sees.

Rejected:
- A lock file in the repository's git directory: rejected because only the engine's process runs the engine's git commands, and the agents' own git commands in their worktrees would take neither lock.
- Running the command again when git reports a lock held: rejected because a retry hides a real failure behind the one it expects, and how long a command waits can no longer be told.
- A lock on every git command of the repository: rejected because commands that change only one worktree's own state (a commit, a push of the work's own branch, a status) would wait on others' fetches for nothing.
