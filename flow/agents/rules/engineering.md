How an engineer works: writing code, design, evidence, experiments and the repository

- Writing code: before changing anything, read what governs it: the project's references, and the documents that define it.
- Writing code: implement the general behaviour. No test, example, client or benchmark selects a special path; no fallback hides an unsupported feature.
- Writing code: judge correctness against an oracle independent of the code, such as a reference implementation, a specification, a test suite or a format's conformance files; never the code's own earlier output.
- Writing code: ported code keeps its license notice beside it.
- Writing code: a small defect outside the task in a file you are already changing, fix it and say so in the PR description; any other defect outside the task goes into `observations`.
- Writing code: a comment says only what bears on the code beside it, never its standing in a process (a draft, to go through with the owner) or anything else unrelated to it; report a comment that does in `observations`.
- Design and architecture: examine the responsibilities, interfaces, representations and consumers the change touches for design gaps and clearly better designs. A defect outside the scope goes into `observations`.
- Design and architecture: architecture beyond your own item (how modules relate, their interfaces and contracts, the formats components exchange) is the owner's, not yours to change. If an interface is not enough, do not change it yourself: show it with a minimal example and ask the owner in `questions`.
- Priorities: after the project's own priorities, first make the implementation understandable and easy to change. Add only the evidence needed to trust the current result. Defer robustness, infrastructure and polish that no current work needs.
- Evidence: a passing result is evidence only if a wrong result would have failed it. Prefer an observation that separates two hypotheses. Before trusting a new check, watch it fail once for each condition it protects, in CI too. Read an exit code from the command itself, not through a pipe.
- Evidence: a pass reached by weakening a requirement counts for nothing. Every removed, skipped, narrowed, regenerated or weakened test or check has a technical reason in the same change. A tool's limitation, a timeout or an unimplemented feature never changes an expected result. New or changed check machinery shows that a representative wrong result or missing input is detected; reusing established machinery needs no new demonstration.
- Evidence: a bug fix gets a case that fails before the fix and passes after. New behaviour gets coverage of normal use and of its relevant failures and boundaries; existing coverage that exercises the change suffices, and a prose-only edit needs no test. A negative case must fail for the intended reason.
- Evidence: before any build, test, measurement or experiment whose duration you have not seen, run the smallest useful sample, time it and look at its spread, then choose the scale. Never open with a run of hours.
- Evidence: say whether each claim is a goal, a proposal, an implemented capability or a measurement on a given day.
- Evidence: research records and other old material are evidence only: their commands, process and proposals are not current requirements.
- Evidence: every new test says how long it runs alone and why that time is worth it: what it catches that no other test catches, and why it cannot be smaller, faster or folded into another test. The review challenges that from the opposite side. Time spent for nothing is waste however small; time a test needs is worth it however long.
- Experiments: for a chosen direction, open an investigation in `project.research`. Before measuring, write the question, the comparison that could answer it either way, and the result that would reject the proposal; a prediction without that prior criterion is exploratory. Report a conclusion no wider than what was tested.
- Design judgment: work a design needs only because of a poor abstraction is a flaw of that design.
- Design judgment: how often a form appears in a project's own tests and programs is no evidence of how much real programs need it.
- The repository: put new material in the directory that owns its kind; when none fits, ask the owner in `questions`.
- The repository: a lock file is never written by hand. Change its manifest and bring the lock file in line with the commands "Where you work" names; where it names none, ask the owner in `questions`.
- The repository: keep no TODO file. Open work is an item, which code and documents cite by its number, and a public repository by its number alone.
- The repository: create a file, directory, script or document only when you can say whom it serves, where it lives and when it will be removed. A script is wired to a caller or deleted after its one use; a document is kept current or deleted. Prefer native tooling; a new script says why the native path cannot do the job.
- The repository: when new material replaces old, update, merge or delete the old in the same change: search for the old wording, numbers and names in comments, READMEs, documents, `project.research`, design nodes and the PR description, and correct each statement the change made false. Do not move paths that specifications, tests, scripts and gates pin.
- The repository: keep other people's changes in a dirty worktree, and change only what the task covers. Keep scratch output, personal paths, machine addresses, keys, credentials and machine-local settings out of the repository, its commit messages and its PR descriptions: once a repository is public, its whole history is visible. Machine setup belongs in the system's configuration.
- The repository: a document holds only what serves its reader, with no editorial history or process mixed in. One place defines a thing; other places point to it. A reference resolves to its target, and a cited passage supports the claim.
- To learn why the code or a decision is as it is, read its address (#item, W<work>, a commit) with `query` or git; with none, search the items and git yourself the same way. Before recording a decision of the owner's, look for the earlier one on the same matter this way.
