- 消息是异步的：没有 session 等着回复。阻塞的是问题本身，问人只是解决它的一种办法，系统只在问题所在之处阻塞，而每个 ask
  都会指明那个地方。如果每个问题都有一条自己的、离开流程再回来的路，一连串问题就可能让状态失控，回去的路也可能走不通。

- owner、助理、架构师和流程维护者之间的每条消息都经过同一个消息中心，由它投递、保存消息的状态并执行下面的规则；
  谁都不直接往别人的输入里写。owner 的收件箱、助理可以读的东西、架构师在一轮中拿到的消息，都来自它。各自带有状态、
  已读标记和计数的独立渠道彼此对不上，让有些消息无从回答，有些计数无法清零。

- 一条消息要么是告知，无需回答，要么是 ask，需要回答。附带报告、agent 告诉 owner 的话、
  agent 关于流程的报告和引擎的通知，都是告知；提问和审批都是 ask。过去每个渠道都为这两种东西之一长出了自己的一套机制。

- 发送者通过回答是或否来说明一条消息关于什么：是否只有人能解决，比如权限或额度；是否涉及条目本身、其他条目或项目的进度，
  值得立条目的缺陷也在其中。消息中心的规则写在流程定义里，也画在流程的图上，按第一个成立的回答投递：
  第一个成立就发给 owner，第二个发给项目的架构师；流程本身的毛病不走这条路，
  写进关于流程的报告 (flow/returns.md, "agent 在它的返回里报告流程的毛病")；架构师在其职责之内解决不了的，再转给 owner。
  以前发送者必须知道谁处理什么，于是每当某类事情改由别人处理，它的图就得重画。各自会改变处理方式的问题种类被去掉了：
  被问者凭问题本身说的内容来判断它，而这些回答只用来选队列。

- 做不下去是条目的工作里每个 agent 格子都有的一条出路：缺了只有别人能给的东西，工作无法靠继续往下走来解决。
  它用 owner 的语言写明缺什么、为什么需要、试过什么，并说明属于哪一类，由类别决定谁来定 (flow/asking.md,
  "发送者通过回答是或否来说明一条消息关于什么")：只有人能解决的，owner 定；条目本身要改的，架构师定；
  两类都不是或分不清的，也是 owner 定，免得 agent 硬选一类、送到定不了它的人那里；流程本身的毛病除外，写进关于流程的报告。
  每个格子的这条出路都进同一个等待的引擎格子，放行后回到它来的那个格子，
  在同一个 session 里接着做，带上决定者放行时说的话 (flow/asking.md, "消息是异步的")；owner 也可以取消工作，
  架构师也可以改了条目、让工作从头开始。引擎自己的故障，比如断网、登录失效或命令行崩溃，不走这条路，
  由引擎处理 (backend/engine/failures.md, "断网造成的失败一律同样处理")。

- 消息从产生之处带上它关于什么：从条目的工作里交出去的，带条目、其工作和格子；架构师发的，带事项和它提到的条目；
  owner 在某个条目下写给架构师或助理的，带这个条目。消息与那个条目一起显示，随其工作或事项一起撤回，
  并连同这个 context 交给接收者。不需要另设一个用来归档消息的主题概念。

- 进错了队列、或属于另一个项目的架构师的消息，由收到它的人转交：owner、助理或某个架构师。转交的 ask
  保留原提问者，原先扣住的也仍然扣住，回答回到原提问者那里。流程维护者的消息只按它自己那条决定所允许的方式转交。
  消息中心不可能总把消息放对，而架构师处理不了别的项目的消息。

- 流程维护者是一个面向 wf-agents 自身流程和引擎的队列：agent 关于流程的报告、流程的异常、wf-agents
  自身的故障（比如缓存失效）、引擎关于这些故障的通知，以及引擎因其中某项而暂停的工作，这种工作在原因查明后重新启动。
  owner 和助理处理这个队列，因为设计流程是他们的事；助理可以把其中一件转给构建引擎所用的那个项目的架构师，
  绝不转给别的架构师。跑在别的项目上时，wf-agents 的故障仍须在 wf-agents 里修好；若让它们自己转出去，就会到达绝不能碰
  wf-agents 的架构师那里；而在规则里点名一个项目，又会把流程绑定在这个项目上。

- 助理是 owner 的另一个自己：它可以读发给 owner 的一切，靠自己去看，没有任何东西推送给它；它照 owner 的吩咐做事，
  拥有 owner 给它的、任何工程师都没有的广泛权限。除非 owner 让助理代答，否则没有人代替 owner 回答；在那之前，ask
  只扣住它指明的东西。若消息一来就推送给助理，就会打断它正与 owner 讨论的事，而它的 context 必须留在那件事上。

- owner 在条目下写的话，要让架构师或助理收到，就点名它们，给架构师的话作为 owner 的话进入它的队列，
  因为架构师和助理做的是不同的事；不点名的，是条目讨论里的评论 (items.md, "条目分成几块")，
  有工作在进行时由它的 agent 收下，格子中途也随工具的结果送到 (flow/inputs.md, "条目的各块是有条件的输入")，
  因为 owner 是顺带着引导工作的；评论只是说话，不改变工作的路线 (flow/questions.md,
  "owner 在每个问题上要么选一个选项")。

- ask 是一个是/否问题，或在若干选项中选一个或多个，附有提问者推荐的回答。答“否”要附理由，答“是”不用，
  选择可以附理由。只有在 ask 上给出的回答才算回答了它：旁边的话都是告知。引擎发出的 ask 不作判断，也不附推荐：
  流程要求的审批，比如对流程改动的审批，用是或否回答；只有人能清除的故障，比如登录失败，以清除它作为回答，
  不需要写任何东西。用自由文字写的问题没法快速回答，而问题旁边的话若被当作它的回答，就无法与讨论区分开。

- 被问者可以不回答，而是就这个 ask 提问：这一问发给提问者，架构师那边被扣住的事项会排到队列最前面回来；
  提问者用一条告知或修改 ask 来回答。改过的 ask 是一个新版本：对旧版本的回答不沿用。已经回答的 ask 不再修改，
  而是另问一个新的。提问者也可以撤回自己的 ask。

- 架构师的 ask 扣住提出它的那个事项，而不扣住架构师本身，架构师在此期间去处理下一个事项 (flow/architect/matters.md,
  "架构师一次处理一个事项")。

- owner 没有回答的 ask 没有期限：它一直开着，直到被回答、修改或撤回。期限和自动失效都太复杂。

- ask 发出之前，消息中心机械地找出与它相似的未决 ask，交给提问者，由提问者加入其中一个或单独提问；
  这样一个回答就放行所有等着它的工作。否则，同一个原因会从每个工作各到被问者那里一次。由一个小模型自行合并 ask
  的做法没有采用：两个 ask 是否相同需要判断，而判断属于图上的 agent，提问者也最了解自己的 ask。

- 不再有人等的 ask 由消息中心撤回，并说明原因：扣住工作的 ask，若其工作已结束或被取消；架构师的 ask，
  若其事项已处理或已撤回。扣住工作的卡口，即做不下去的等待和问题的卡口，也在工作结束或被取消时撤回。
  架构师的 ask 比架构师的工作活得长，架构师的工作在其队列空了时就结束。这样的 ask 若一直开着，就被算作等待中，
  却无法清掉，还要 owner 去决定已经无关紧要的事。

- 流程改变时，ask 把它的工作扣在新版本把原格子对应过去的那个格子上；新版本没有对应的格子时，ask 被撤回并说明原因，
  若仍需要就重新提问。架构师的 ask 比因新版本而结束的工作活得长，它们扣住的事项会随回答一起回来。

- 没有防止重复问已回答问题的机制：能提问的一轮看得到它自己工作里未决的问题，以及与它的问题相似的 ask，双方都能判断，
  所以不会没完没了地来回。这种机制只会浪费 token，随每一批都附上一条禁止重复提问的规则也一样。
