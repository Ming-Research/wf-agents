### decision line-kind-in-the-flow
Whether the agents of a line only read, or change only the project's tests, is said by that line in the flow's definition, never by a cell of it. A line that says neither writes what it will.
Why: A list of line names kept by the engine or by the installation would name parts of the flow outside it, and would go wrong without anyone seeing when a line is added or renamed. The flow is what the owner reads and approves, and its line's file is where the owner sees the line's kind. It is the line's because its agents are told it in the system prompt of the line's session, which every cell of the line shares (principle the-system-prompt-holds-what-a-line-shares). That the kind is said in the flow rests on judgment, not on a case.

### decision a-line-of-tests-is-held-to-what-its-run-changed
As a round of a line that changes only the project's tests ends with a return that does the cell's work, the return is sent back for each file that `[tests] paths` of `project.toml` does not take in, of those the branch's head differs in from its head as the run's first round began that are of the work's own change. The line is refused nothing more than a line that writes, and is told the paths of the tests in place of the lock commands. A look that cannot be made fails the round, and a project that names no tests keeps the engine from starting with such a line.
Why: From the run's beginning, a file a round sent back left changed is seen again as the next round ends, and what other lines committed before the run is not the line's; the round's own commits alone would let a later round pass on what an earlier one left, and what was pushed before, which the old engine counted from, is no beginning here, since `run_tests` pushes within the round. A file main's merge brings in as main has it is no change of the work's. The look, not a refusal, holds the line (principle refuse-as-little-as-must-be), and a lock file is none of the tests. Nothing after the round holds the line to its tests, so a look that failed or a project with no tests, let through, would take any change for tests (principle nothing-passes-for-normal).

### decision rules-are-the-engines
The engine's heavy commands are refused on every installation. An installation's settings may add heavy commands, and lock commands that may run under a heavy command, but no lock command that is a heavy command whole or that pushes. Settings that would otherwise undo the engine's rules are refused when they are read.
Why: The engine pushes and has the project checked, and a project on another toolchain names its own commands in its configuration (Article 1). How wide a lock command under a heavy one may be is the installation's judgment. What stays open: rules in the settings files of the program's own configuration directory, which the engine does not read, and a heavy command the shell reaches by another name.

### decision lock-commands-under-heavy-ones
On a line that writes, the lock commands the settings name, which update a lock file and build nothing, are allowed, even though the heavy commands they fall under are refused. Where the installation allows some other use of such a heavy command, the engine refuses that use again. Where the installation allows the whole heavy command, or every command, the heavy command is refused whole and its lock commands are not allowed.
Why: Agents that could not regenerate a lock file wrote it by hand, or stopped and waited for someone. But the command line refuses whatever any rule refuses, so refusing the heavy command whole would refuse its lock commands as well, and leaving out the refusal without refusing the installation's rules again would let a build through.
